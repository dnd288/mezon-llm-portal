## Context

The portal is a single Next.js 16 app. Styling is Tailwind v4 + shadcn/ui v5 (base-ui). The
current `globals.css` defines stock shadcn oklch tokens in `:root` and `.dark`. No `next-themes`
provider is wired — the `.dark` class variant is unreachable. All 9 screens use hardcoded
Tailwind utilities.

The design document defines a complete palette with 30+ tokens across two themes, toggled via
`data-theme` attribute on `<html>`. The gradient is theme-invariant. Geist + Geist Mono fonts
are already loaded.

## Goals / Non-Goals

**Goals:**
- Replace the CSS token system in one change — no gradual migration.
- Wire `next-themes` for dark/light switching with `data-theme` attribute.
- Customize shadcn/ui components to match the design kit.
- Update all screens to consume the tokens.

**Non-Goals:**
- No new functionality or routes.
- No test suite (OQ1 — test infrastructure is a separate concern).
- No model card enrichment beyond what the current API returns (sparklines, latency, TPS are
  design-ready placeholders if the data isn't available).
- No i18n changes — copy stays as-is.

## Decisions

### 1. Token naming: use design-doc short names directly

Use `--g1`, `--g2`, `--bg`, `--surf`, `--tx`, `--mut`, etc. as CSS custom properties on `:root`.
Map them into Tailwind v4 via `@theme inline` so they're available as `bg-[var(--bg)]` etc.
Also map the key design tokens to shadcn semantic slots (`--background`, `--foreground`,
`--primary`, etc.) so existing shadcn components pick them up without per-component overrides
where possible.

**Why not a full rename?** The shadcn semantic names (`--card`, `--muted`, etc.) don't map 1:1
to the design-doc vocabulary. Keeping the design-doc names as the source and mapping to shadcn
slots avoids a naming translation layer that would drift.

### 2. Theme switching: `next-themes` with `attribute="data-theme"`

The design document uses `[data-theme="light"]` for the light variant. `next-themes` supports
custom attribute mode. Set `defaultTheme="dark"` since the design is dark-first. The
`@custom-variant dark` line in `globals.css` changes from `&:is(.dark *)` to
`&:is([data-theme="dark"] *)`.

### 3. Component customization: override shadcn component files directly

The shadcn components in `src/components/ui/` are already project-owned (generated by shadcn CLI).
Override `button.tsx`, `badge.tsx`, `tabs.tsx`, `input.tsx` directly rather than creating a
wrapper layer. This is the standard shadcn approach — components are meant to be modified.

### 4. Screen updates: incremental within one PR

Update each screen file to use design tokens. Replace hardcoded Tailwind classes (`bg-gray-900`,
`text-gray-400`) with token references (`bg-[var(--bg)]`, `text-[var(--mut)]`). Large screens
may benefit from extracting repeated patterns into CSS utility classes in `globals.css`.

## Risks / Trade-offs

- **Visual regression risk** → Mitigated by visual inspection against design doc. No automated
  visual testing exists (OQ1).
- **Large diff** → Acceptable because the change is purely cosmetic with no behavioral impact.
  Reviewing is straightforward: check tokens match design doc, check screens use tokens.
- **shadcn component upgrades** → Customized components may need manual merge on shadcn updates.
  This is the documented trade-off of shadcn's approach.

## Migration Plan

No migration needed. This is a cosmetic change. Deploy replaces the old visuals entirely.
No rollback beyond reverting the commit.

## Open Questions

None blocking. OQ1 (test suite) is acknowledged but does not gate this change.
